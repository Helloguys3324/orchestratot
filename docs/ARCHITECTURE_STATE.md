# ARCHITECTURE_STATE.md

## Genesis Protocol: Current System Architecture

### 1. High-Level Objective
Build a highly scalable, fault-tolerant Multi-Agent Orchestrator operating in a continuous, zero-human-in-the-loop, multi-week execution pipeline. The system utilizes DAG-based routing, asyncio, and MCP (Model Context Protocol) integration.

### 2. Current Repository Structure
The repository is structured into the following directories:
- `.github/`: CI/CD workflows, automation scripts, and task queues for AI Factory.
- `backend/`: Core orchestrator logic utilizing FastAPI, Uvicorn, and Pydantic v2.
  - `agents/`: Defines agent classes and behaviors.
  - `api/`: FastAPI APIRouter endpoints decoupling application routing logic, utilizing FastAPI's `Depends()` injection and unified helper functions (like `_get_item_or_404`) to reduce boilerplate for reusable API dependencies.
  - `llm/`: Decoupled low-level LLM API integrations (e.g., Gemini Live API and OpenAI compatible endpoints) enforcing strict architectural boundaries.
  - `models/`: Pydantic data models. Utilizes reusable helper functions (e.g., `_get_models_by_category`) to extract recurring list comprehensions for maintainability.
  - `sessions/`: Manages orchestration sessions.
  - `skills/`: Agent capabilities.
  - `tests/`: Unit and integration tests for backend modules.
  - `websocket/`: Real-time communication handlers.
  - `state.py`: Global application state and manager instantiations.
- `docs/`: Architectural Decision Records (ADRs) and architectural state documentation.
- `frontend/`: Web UI components (HTML/CSS/JS) with shared UI utilities and Node.js testing.
- `skills_library/`: Reusable skills and MCP tools.
- `tests/`: Unit tests for `skills_library` and other non-backend modules.
- `data/`: Persistent or temporary data storage.
- `workspace/`: Execution workspace for agents.

### 3. Tech Stack Choices
- **Backend Framework:** FastAPI, Uvicorn (async HTTP server)
- **Data Validation:** Pydantic v2 (includes SecretStr for config security and request models)
- **Concurrency:** Asyncio (Python) for non-blocking operations.
- **Environment Management:** `pydantic-settings` for configuration loading, robust parsing, and environment variable overlay prioritization over JSON fallbacks, including bypassing invalid empty variables. Use `pydantic.Field` boundaries for numeric fields to ensure out-of-bound variables reliably trigger `ValidationError`s. When configuring directory paths from environment variables, subsequent directory creation calls must use `parents=True` to guarantee nested directories are created safely without raising `FileNotFoundError`. Legacy JSON configurations (`data/settings.json`) are automatically migrated to environment variables (`.env` file) on startup, securing credentials by deleting the legacy file after migration. To prevent boot-loops from corrupted legacy data, this migration is wrapped in a `try...except ValidationError` block with a `finally` clause ensuring the legacy file is deleted regardless of success. In Python modules, when using `os.getenv` to set global or module-level variables from environment variables, ensure `dotenv.load_dotenv()` is executed before those variables are initialized. Furthermore, when assigning fallback path values from environment variables using `os.getenv` in Python, prefer the `os.getenv('KEY') or default` pattern over `os.getenv('KEY', default)`. This ensures that explicitly defined but empty strings (e.g., `KEY=''` in `.env`) correctly resolve to the default value instead of being interpreted as the current directory. When introducing new configurable system paths or directories (e.g., workspaces, data directories) or fallback models, define and expose them centrally in `backend/config.py` using the `os.getenv('KEY') or default` pattern, rather than hardcoding them locally in individual modules. When overriding the default `.env` file path for tests, dynamically override `backend.config.ENV_FILE` and reload `DotEnvSettingsSource` to ensure complete determinism without mutating global files.
- **Protocol:** MCP (Model Context Protocol) for tool and skill execution.
- **Routing:** DAG-based (Directed Acyclic Graph) task routing.
- **Testing:** `pytest` (backend) and Node.js built-in `node:test` (frontend, leveraging conditional CommonJS exports to expose vanilla JS objects, achieving complete line coverage, and simulating DOM manipulation via `global.document` mocking without external libraries) with heavily type-hinted, asynchronous code. When writing Python test functions, ensure they are explicitly type-hinted with `-> None`. When invoking tests locally after manually installing dependencies, or when facing `ModuleNotFoundError`, execute tests using `PYTHONPATH=. python -m pytest` instead of standalone `pytest`. For config models, validate dynamically via `model_fields.keys()` rather than `model_dump()` to prevent environment-dependent crashes. When testing configuration logic that interacts with `.env` files (e.g., in `backend/tests/test_config.py`), do not mutate the project's root `.env` file. Override the `AUTOGEN_ENV_FILE` environment variable to point to a temporary file path to ensure test determinism and prevent overwriting local environment states. When testing Python modules for environment variables evaluated at module-load time, use `subprocess` with a mocked `env` dictionary instead of `monkeypatch.setenv`. When testing Python code that involves disk I/O for configuration files, always mock the file paths or use `pytest`'s `tmp_path` fixture to prevent destructively overwriting the local filesystem. When writing or modifying Python test functions, enforce explicit `-> None` return type-hinting. For async tests in pytest, prefer using `@pytest.mark.anyio` instead of `@pytest.mark.asyncio`. The `anyio` plugin is natively available via the project's FastAPI/HTTPX dependencies. When writing tests for FastAPI WebSocket connection managers, use `unittest.mock.AsyncMock` to mock the `WebSocket` object and properly await its asynchronous methods (e.g., `await websocket.accept()`). When refining error messages or validation logic, ensure that any changes to exception messages or conditions are carefully synchronized with existing test assertions (e.g., `pytest.raises(..., match=...)`) to prevent breaking tests. Conversely, if preserving old behavior, ensure your new logic does not inadvertently alter the exact strings or types expected by existing tests. For Node.js native tests, always pass explicit file globs (e.g., `frontend/tests/*.test.js`) instead of directory paths to avoid module resolution errors. When mocking global objects like `global.document` in Node.js tests, always include a cleanup step in a teardown hook to prevent test pollution. When writing unit tests that expect an exception to be thrown, always include an explicit failure assertion (e.g., `assert.fail()`) inside the `try` block immediately after the target call to ensure the test fails if the exception is incorrectly not raised. When introducing new exception handling paths (e.g., explicitly catching and re-raising a base custom exception to prevent double-wrapping), you must add dedicated unit tests asserting that the base exception is correctly raised and not inadvertently wrapped by generic catch-all blocks. For Node.js modules that conditionally attach event listeners upon evaluation, test setups must clear `require.cache` and re-require the module after establishing global DOM mocks to ensure proper listener attachment. When interpreting Node.js native test coverage reports (`--experimental-test-coverage`), uncovered lines reported within test files (`.test.js`) are often expected `assert.fail()` calls inside `try...catch` blocks that properly verify exceptions; do not attempt to 'fix' these uncovered lines. Also, running a single test file will only report coverage for code executed during that specific test run, which may falsely appear as a drop in overall coverage; always run the full suite to get an accurate representation of total file coverage.
- **Dependency Management:** Proactive vulnerability mitigation (e.g., upgrading packages to avoid insecure transitive dependencies like `diskcache`) and explicit local vulnerability scanning utilizing `pip-audit`, which requires core backend dependencies to be installed first to ensure accurate evaluation of transitive dependencies. When evaluating vulnerabilities for specific older package versions (e.g., defined with `>=` constraints), those exact versions must be installed locally first, rather than relying on the requirements file which resolves to the latest compatible versions. Safe dependency upgrade paths must be formally documented in `docs/API_NOTES.md` or similar documentation. Note that version 0.4.x of `pyautogen` introduces massive breaking API changes; do not upgrade `pyautogen` to `>=0.4.0` as it will fatally break backend logic without a complete application rewrite. Unmitigable vulnerabilities in older pinned versions must be documented in `docs/API_NOTES.md`.

### 4. Data Flow & System Architecture
1. **Input:** User requests or autonomous triggers initialize a session.
2. **Orchestrator:** A central asynchronous loop manages DAG execution.
3. **Agent Routing:** Tasks are parsed and assigned to specific agents based on capabilities.
4. **Execution:** Agents use skills via MCP, fetching tools and executing them safely. Managers (e.g., `SessionManager`) isolate real-time WebSocket communication from core logic by utilizing injected `_message_callback` functions to emit events (e.g., `_add_message`), decoupling them from direct FastAPI WebSocket routing. When managing WebSocket connections, the `ConnectionManager.disconnect` method must be used rather than manually discarding the socket from the connection set to ensure empty session trackers are properly garbage-collected, avoiding state leaks. WebSocket connections for real-time updates are tracked using `collections.defaultdict(set)` to simplify session membership management and avoid redundant key-existence checks. Localized helper functions (e.g., `_error_msg`) are utilized for standardized event formatting.
5. **Memory & State:** `ARCHITECTURE_STATE.md` maintains long-term memory for the continuous loop, alongside structured logs or databases for session memory.
6. **Output/Feedback:** Results are aggregated, validated against constraints, and returned to the user or passed to the next DAG node. Continuous self-healing is triggered on failure.

### 5. Active Interfaces
- **HTTP Server:** `http://localhost:8000` (FastAPI/Uvicorn) entry point via `run.py`.
- **WebSocket:** Real-time updates and streaming between backend and frontend.

### 6. Architectural Constraints & Cognitive Directives
- **Performance:** Optimize algorithmic complexity (prefer O(1)/O(N)), memory management, and execution speed.
- **Verification:** Zero-trust verification. Unit/integration tests via MCP must pass before any code is considered complete. Furthermore, strict frontend visual validation is required for any UI modifications to confirm layout stability and absence of console errors before changes can be submitted. Playwright is not used for UI testing; UI validation relies on manual visual inspection and the native Node.js test runner (e.g. `node --experimental-test-coverage --test frontend/tests/*.test.js`). When testing backend logic that generates file artifacts (e.g., writing custom skill Python files or updating local JSON databases), ensure these artifacts are explicitly removed or unstaged (e.g., using `git restore --staged` and `rm`) before submission to avoid committing unintended state data and violating repository constraints.
- **Self-Healing:** Enter a debug loop immediately upon test failure or bug detection. Analyze stack traces and fix.
- **Recursive Meta-Prompting:** All tasks generated must follow the strict 4-part protocol: `[INPUT STATE]`, `[ATOMIC OBJECTIVE]`, `[CONSTRAINTS]`, `[ACCEPTANCE CRITERIA]`. To comply with the Specificity Rule for the final submission step using the `done` tool, the step description must explicitly specify the tool name (e.g., the `done` tool) and include the fully expanded, literal multi-line markdown template text for `## Validation Results` and `## Frontend Walkthrough` (including all placeholder options like PASSED, FAILED, YES, NO, NOT APPLICABLE) alongside the required PR title. When defining execution plan steps to modify files, explicitly include the exact, literal implementation details within the step description (e.g., providing the exact `<<<<<<< SEARCH` and `=======` blocks for `replace_with_git_merge_diff`, or the complete inline Python script for `run_in_bash_session`), avoiding vague, high-level summaries of intended changes. Every execution plan step that modifies a file must be immediately followed by a step to verify the exact changes made, using a command like `git diff`. To comply with the Specificity Rule, execution plans must not contain purely analytical, mental, or research steps (e.g., 'Analyze history', 'Calculate differences', 'Note that', 'Conclude that'); all analysis must be performed prior to defining the plan, ensuring every step is a concrete, actionable tool call stripped of conversational filler, internal monologue, reasoning, and rhetorical questions. Structure the plan strictly as a numbered list of concrete, actionable steps. When creating an execution plan, do not include steps for actions that were already completed during the exploration phase. If modifications were made during exploration, begin the plan with a concrete validation check of those pending changes (e.g., `git diff`); if no files were modified, do not use `git diff` to check the initial state as it will be empty and violates the Groundedness Rule. To comply with the Groundedness Rule, do not assume dependencies are already installed; the validation plan step must explicitly list the commands to install both backend dependencies and test packages (e.g., `pip install -r backend/requirements.txt && pip install pytest pytest-asyncio`) before executing the test command. Furthermore, when appending code to an existing file, do not assume necessary modules are imported; first verify their presence (e.g., using `grep`) before relying on them. When citing test coverage metrics in an execution plan, use tools like `tail -n 20` or output redirection when running the coverage command to ensure the final summary table is fully visible in the un-truncated bash output, as claims based on truncated outputs will be rejected. When an execution plan concludes that no meaningful safe change exists, do not create a separate, purely analytical plan step to 'report' this. Instead, incorporate the concluding statement directly into the description of the final step that uses the `done` tool. To comply with the Completeness Rule in execution plans, always insert an explicit step immediately before the pre-commit step to run all mandated validation commands (e.g., `python -m compileall`, `pytest`, `scan_secrets.py`) to verify the final code state, even if no files were modified during the task. To comply with the Pre-Commit Rule in execution plans, the pre-commit action (e.g., calling `pre_commit_instructions`) must be a distinct, standalone step immediately before the final submission step, and the step description must exactly match the required string: 'Complete pre-commit steps to ensure proper testing, verification, review, and reflection are done.' (including exact capitalization, punctuation, and hyphenation). Do not wrap this required string in markdown formatting like italics (`*`) or bold (`**`). If no files were modified during a task, skip all pre-commit validation steps that are contingent upon a code change, including `request_code_review` and frontend UI verification.
- **Error Handling & Validation:** Enforce explicit typed domain exceptions. Fields extracted from dynamically typed payloads (like untyped dictionaries) must have explicit data type validation (e.g., using `isinstance()`) within the core domain logic layer to prevent unhandled server errors. Intercept generic exceptions (e.g., `AttributeError` from calling `.get()` on a `None` payload, `TypeError`/`ValueError` during URL parsing, or `TypeError`/`KeyError` when parsing malformed underlying JSON databases) within the core domain logic layer and re-raise them as explicit domain-specific errors, rather than adding generic exception handlers to the API routing middleware. When using `urllib.parse.urlparse` to parse URLs, explicitly catch `ValueError`, `AttributeError`, and `TypeError` to properly handle invalid formats. Since `urlparse(None)` in Python 3.12+ returns `ParseResultBytes` with scheme `b''` instead of raising an exception, ensure scheme validation correctly handles or rejects `bytes` objects rather than assuming the scheme is always a string. When refactoring dictionary accesses within `try...except (TypeError, KeyError)` blocks that validate malformed data, avoid replacing bracket notation (e.g., `s['id']`) with `.get()`. Using `.get()` on non-dictionary types (like strings) raises an `AttributeError`, which bypasses the expected `TypeError` handler. When catching low-level exceptions like `OSError` or `json.JSONDecodeError`, or specific HTTP client exceptions (e.g., `httpx.HTTPStatusError`, `httpx.RequestError`), explicitly re-raise them as specific domain errors (e.g., `SkillInstallError`) instead of generic `Exception`, chaining `from e` to preserve original tracebacks, and mapping to precise HTTP status codes. When wrapping generic exceptions in typed domain errors (e.g., converting `Exception` to `SkillError`), ensure you explicitly catch and re-raise the base custom exception first (`except SkillError: raise`) before the catch-all `except Exception as e:` block to prevent double-wrapping or obscuring already-typed errors. Use standard synchronous `@contextmanager` from `contextlib` to wrap asynchronous FastAPI route handlers for centralized HTTP status mapping, eliminating duplicate `try...except` blocks. Use shared base request models to reduce duplication in API contracts. Pydantic request models for the FastAPI backend (e.g., for agents, sessions, and skills) are centralized in `backend/api/schemas.py` to prevent code duplication and resolve potential circular imports, rather than being defined inline in individual router files. Use Pydantic `BaseModel` for inbound request payload validation, and `pydantic-settings` for config management (configured with `env_ignore_empty=True` to ignore empty strings for most fields and prevent overwriting defaults) with empty env var filtering via `os.environ.pop`, dynamic `ValidationError` fallback using explicit defaults via `init_kwargs`, replacing hardcoded `.env` path logic with support for environment variable fallback (e.g., `AUTOGEN_ENV_FILE`), prioritizing environment variables when merging paths, safely handling empty strings in path variables via `_get_path_env`, and persisting only explicitly provided keys during runtime `.env` updates to avoid cluttering with defaults. When clearing optional configuration values programmatically, use `dotenv.unset_key` to remove the key from the `.env` file and `os.environ.pop` to remove it from the runtime environment, rather than writing an empty string. The application intentionally writes UI-driven configuration changes back to the `.env` file dynamically (e.g., via `save_settings` using `dotenv.set_key` in `backend/config.py`); do not treat this as an anti-pattern or attempt to remove it, as it is a required feature. When implementing settings update APIs that interact with partial configuration payloads, pass the incoming payload dictionary directly to the persist function rather than merging it with the full application settings first, preventing partial updates from inadvertently persisting application defaults. To reduce logic duplication when extracting, defaulting, and type-checking multiple fields from input dictionaries, extract this logic into dedicated helper methods (e.g., `_validate_string_field`).
- **Code & Pattern Conventions:** To improve code readability and conciseness when aggregating or filtering data, prefer list and dictionary comprehensions (utilizing the walrus operator `:=` to avoid redundant calls if necessary) and `next()` generator lookups over verbose `for` loops. When refactoring loops into comprehensions where the loop body contains complex logic like `try...except` blocks, extract that logic into a localized helper function (e.g., `def _read_content()`) to keep the comprehension clean. To concisely merge configuration dictionaries with a priority order (e.g., data overriding base overriding defaults) while filtering by allowed keys, use dictionary unpacking (`{**defaults, **base, **data}`) and dictionary comprehensions (e.g., `{k: merged[k] for k in UPDATABLE_FIELDS if k in merged}`) instead of verbose `if/elif` fallback loops. When programmatically filtering or validating fields against a Pydantic v2 model, dynamically access the valid field names using `Model.model_fields.keys()` (e.g., `ConfigModel.model_fields.keys()`) rather than relying on hardcoded lists or sets. In Pydantic V2, when programmatically extracting default values from `model_fields` (e.g., `ConfigModel.model_fields[k]`), you must handle both static `.default` attributes and dynamic `.default_factory` functions to accurately retrieve fallback values. To reduce logic duplication and boilerplate, managers (e.g., `AgentManager`) extract shared configuration lists as class constants (e.g., `UPDATABLE_FIELDS`) and use them dynamically to manage attributes. Centralized event logging mechanisms (e.g., `_add_message`, `_sys_msg`, `_error_msg`) decouple message formatting and WebSocket emission from specific business flows, drastically reducing duplicated exception handling boilerplate. If git commands or `reset_all` fail with an error indicating `Unable to create '.git/index.lock': File exists.`, execute `rm -f .git/index.lock` via bash to clear the stale lock. When querying the local Git history, be aware that the repository may be a shallow clone. If standard commands like `git log` fail to show older history, query the remote tracking branch directly (e.g., `git log origin/main`). When modifying extremely long lines where the full text cannot be confirmed due to bash output truncation, avoid using `replace_with_git_merge_diff` with massive, unconfirmed `SEARCH` blocks. Instead, use `run_in_bash_session` to create a Python string replacement script via a heredoc (`cat << 'EOF' > script.py`), perform an exact replacement of a confirmed short substring, execute the script, and explicitly remove it. When executing Python scripts via bash that contain complex string literals or multiple levels of quotes, prefer writing the script to a temporary file using a heredoc (`cat << 'EOF' > script.py`) and executing it, rather than attempting to pass the script inline via `python -c "..."`, to avoid bash parsing and nested quoting syntax errors. When writing these heredoc scripts, include safeguards such as limiting the replacement (`.replace(search, replace, 1)`) or explicitly checking if the target addition is already present (`if new_text not in content:`) to prevent duplicate insertions. When using string replacement (e.g., via Python script or sed), you must first confirm the exact target string was successfully read and is fully visible in the un-truncated trace output (e.g., using `grep -n` or `sed -n`) before proposing the replacement. When generating temporary files during exploration or running background processes for validation, explicitly remove these files before completing the task to prevent committing garbage files.
- **Documentation:** API payloads must be documented in `docs/API_NOTES.md`. When recording or updating project metrics, never invent fake data or placeholder metrics to inflate project quality. If live data is unavailable, explicitly document it as such instead of faking data. When modifying JSON files (e.g., `metrics.json`), do not alter the expected data types of existing fields (such as replacing an integer or array with a string like "Data unavailable") to indicate missing data, as this breaks downstream parsers and implicit schemas. Instead, remove the unsupported keys completely and document their absence in a `notes` array or similar text field. In `.github/ai-factory/metrics.json`, task lifecycle states (`pending`, `claimed`, `running`, `completed`, `failed`, `blocked`, `abandoned`, `obsolete`, `duplicate`) must be grouped under a nested `task_lifecycle` JSON object rather than being flat keys. Similarly, PR lifecycle metrics must be grouped under a structured `pr_lifecycle` JSON object to match this structure and prevent duplicate root-level fields. Furthermore, automation visibility metrics (e.g., `safe_automerge_count`, `manual_review_count`, `recent_failure_reasons`, `health_status`) must be explicitly defined under an `automation` object to comply with visibility requirements, rather than being omitted or noted as unavailable.
- **Emergency Stop:** The `AUTOPILOT_STOP` file acts as an emergency stop signal; automation must immediately halt and the file must not be removed.
